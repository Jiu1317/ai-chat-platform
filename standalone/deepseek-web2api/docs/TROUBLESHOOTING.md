# DeepSeek Web2API 常见问题与故障排查

这份说明只针对 `standalone/deepseek-web2api` 自用实验模块。先不要反复点击发送：同一请求是否已进入网页不明确时，自动重试可能造成重复提问。

## 建议的排查顺序

每次都按以下顺序检查：

1. 两个专用 Chrome 是否仍然打开。
2. 两个窗口是否都已登录 DeepSeek，页面上是否出现验证码、限流或风控提示。
3. 运行 `Invoke-RestMethod http://127.0.0.1:9191/health`。
4. 正常停止，再启动一次：

   ```powershell
   .\stop-deepseek-dual-tab.ps1
   .\start-deepseek-dual-tab.ps1
   ```

5. 先用 `deepseek-chat` 发送一句短文本，确认基础通道恢复；最后再测流式和 `deepseek-reasoner`。

## `9191` 无法连接

表现：PowerShell 提示“无法连接到远程服务器”“连接被拒绝”，或第三方客户端显示网络错误。

处理：

```powershell
.\start-deepseek-dual-tab.ps1
Invoke-RestMethod http://127.0.0.1:9191/health
```

如果仍失败：

- 确认当前目录是 `standalone\deepseek-web2api`。
- 确认已运行 `setup-windows.ps1`。
- 不要同时手动启动第二套 DeepSeek 模块占用相同端口。
- 检查 `9191`、`9192`、`9193` 是否被别的软件占用。

不要为了“解决端口问题”把网关改为监听所有网卡；本自用版应保持 `127.0.0.1`。

## 健康检查只有一个通道就绪

这表示双路网关仍能工作，但当前容量只有一路。分别查看两个专用 Chrome：

- 通道 1：工作进程 `9192`，Chrome 调试端口 `9332`
- 通道 2：工作进程 `9193`，Chrome 调试端口 `9333`

常见原因是其中一个窗口未登录、被误关、停在验证码页面，或对应 Chrome 没有正常启动。先手动处理页面，再运行启动脚本。不要复制另一个通道的 profile 覆盖它；两个登录目录必须保持独立。

## 健康检查返回 `503`

两个工作进程都不可用。请检查：

1. 两个专用 Chrome 是否都存在。
2. 是否能在两个窗口中手动发送普通文本。
3. 登录是否过期。
4. 是否出现验证码、账号异常、地区限制、维护或限流提示。
5. `config.json` 中的端口是否与启动脚本一致。

需要人工处理的验证不要交给守护脚本无限重启。完成手动验证后，再执行 `start-deepseek-dual-tab.ps1`。

## 返回 `401 Unauthorized`

API 请求中的密钥与 `config.json` 不一致。请求头必须是：

```text
Authorization: Bearer 你的本地API密钥
```

不要把真实密钥贴进公开截图或 Issue。若密钥曾被公开，立即生成新的随机值并重启模块。

## 返回 `400` 或模型不可用

第一版只约定以下两个模型名：

- `deepseek-chat`
- `deepseek-reasoner`

检查 JSON 是否有效、`messages` 是否为数组、是否至少包含一条用户消息。附件、图片和生图不在第一版承诺范围内，相关请求被拒绝不表示文本功能损坏。

## 返回 `429`、页面提示繁忙或限流

这是网页服务或账号当前不接受更多请求。正确处理方式是停止继续发送，等待页面恢复，必要时由你本人查看账号状态。

本模块不会也不应该通过换 profile、刷新轰炸、自动重复提交或验证码绕过来逃避限制。双通道也不代表账号限额翻倍。

## 页面出现验证码、重新登录或风控

请在对应专用 Chrome 中手动完成。处理期间建议先正常停止 API，避免请求继续排队：

```powershell
.\stop-deepseek-dual-tab.ps1
```

完成验证、确认网页可以手动聊天后，再运行：

```powershell
.\start-deepseek-dual-tab.ps1
```

不要把 Cookie 导出后交给程序模拟登录，也不要把验证码交给第三方识别服务。

## 消息写入了输入框，但没有发出去

可能原因：

- DeepSeek 网页正在加载或暂时繁忙。
- 页面 DOM 已改版，发送按钮选择器失效。
- 网页拒绝了发送，但输入框还保留原内容。
- 同一通道上一个回答尚未结束。

先观察网页是否真的出现新的用户消息。若没有，不要盲目自动重试；复制文本留存后，正常重启并发送一条最短测试消息。若每次都复现，通常需要更新网页适配器，而不是增加点击次数。

## 网页已经回答，API 还在等待

API 正常情况下从专用 Chrome 收到的回答数据流读取内容，不依赖网页是否持续重绘。若网页已经完成但 API 仍等待，常见原因是浏览器调试连接中断、DeepSeek 的流式格式或结束事件发生变化，或者客户端把读取超时设置得过短。只有主数据流不可用时，程序才会尝试用页面回答区域作保守兜底。

先等待合理时间，确认网页的回答确实停止增长；然后取消客户端请求并正常重启。不要再次点击同一条消息的发送按钮。若恢复窗口后能看到完整回答，但短文本仍稳定复现，请按下方清单提供脱敏信息，以便同时检查网络流解析和页面兜底。

如果短文本也稳定复现，请只提供以下脱敏信息：

- 使用的模型名
- 是否流式
- 大致发生时间和等待时长
- `/health` 的非敏感状态字段
- 删除账号、对话和正文后的错误摘要

不要上传网页完整 HTML、Cookie、profile 或包含聊天正文的日志。

## 流式回答中断或没有 `[DONE]`

先用相同模型测试 `stream: false`：

- 非流式正常：重点检查客户端是否支持 SSE，是否设置了过短的读取超时。
- 非流式也失败：检查网页登录和工作进程状态。

思考模式耗时可能明显更长。客户端超时应覆盖网页实际回答时间，但不要设置无限自动重试。

## `deepseek-reasoner` 没有思考内容

先确认 DeepSeek 网页当前确实允许该账号使用思考模式。网页展示方式可能变化，有时只稳定返回最终答案。第一版以“正确选择思考模式并返回最终回答”为基础目标，不保证永久暴露完整思考过程。

如果网页端也没有思考模式，这是账号或网页能力问题；如果网页端有、API 长期没有，则可能是思考模式按钮的页面结构变化，或 DeepSeek 思考片段的数据流格式变化，需要更新对应适配器。

## 两个请求没有并行处理

依次检查：

1. `/health` 是否显示两个通道都就绪。
2. 两个 Chrome 是否分别连接 `9332` 和 `9333`。
3. 两个工作进程是否分别监听 `9192` 和 `9193`。
4. 两个请求是否几乎同时发出。

双通道只能提供最多两个网页工作槽；第三个请求必须等待。DeepSeek 还可能在账号层限制并发，因此“两个通道健康”不保证服务端一定同时生成两个回答。

## 专用 Chrome 被误关

如果已安装守护程序，`watch-deepseek-dual-tab.ps1` 会在连续检测失败后调用启动脚本恢复。恢复后仍需检查登录状态。

如果没有安装守护程序，手动运行：

```powershell
.\start-deepseek-dual-tab.ps1
```

守护程序只恢复进程，不会替你登录，也不会绕过验证码或风控。

## 正常停止后又自动启动

优先使用 `stop-deepseek-dual-tab.ps1`，不要只关闭浏览器窗口。停止脚本会通知守护程序这是主动停止；直接结束进程会被判断为意外退出并尝试恢复。

若确实只关闭了窗口，可先执行停止脚本，再检查没有请求运行后重新启动。

## 启动脚本会不会影响 ChatGPT Web2API

正常情况下不会。两套模块应完全隔离：

| 项目 | DeepSeek 自用实验版 | ChatGPT Web2API |
|---|---|---|
| 网关 | `9191` | 使用它自己的端口 |
| 工作进程 | `9192`、`9193` | 使用它自己的端口 |
| Chrome 调试端口 | `9332`、`9333` | 使用它自己的端口 |
| profile | DeepSeek 两个独立目录 | ChatGPT 自己的登录目录 |
| 进程状态 | DeepSeek 自己的状态文件 | ChatGPT 自己的状态文件 |

不要手动把两套配置改成相同端口，也不要让它们指向相同 profile。

## 网页改版后怎样判断需要更新代码

网页改版可能影响两层：一层是用于输入、模式选择和单次发送的页面控件；另一层是浏览器收到的回答数据流格式。以下现象同时在两个通道稳定复现时，很可能需要更新适配：

- 网页手动聊天正常，但自动化找不到输入框。
- 消息一直留在输入框，发送按钮没有被正确识别。
- 网页已完成回答，API 始终认为仍在生成或没有返回 `[DONE]`。
- `deepseek-chat` 和 `deepseek-reasoner` 的模式选择与网页不一致。

页面控件适配应优先使用可访问属性、稳定语义和多候选选择器，并在实际发送前验证目标元素；回答流适配则必须继续验证开始确认、增量文字、完成状态和关闭事件。不要依赖易变化的随机 CSS 类名，也不要用屏幕坐标硬点。任何一层更新后都必须重新测试：短文本、流式、思考模式、两路并发、主动停止和登录过期。

## 如何安全提供排错信息

可以提供：

- 脱敏后的错误类型和时间
- Python、Chrome、Windows 版本
- 非敏感的端口状态
- 最小复现步骤

不可以提供：

- Chrome profile 或 Cookie
- `config.json` 真实内容
- API 密钥、账号、手机号、邮箱和二维码
- 原始日志包、浏览器存储、完整页面源码
- 含真实聊天、会话编号或本机用户名的截图

如果必须截屏，先裁掉账号区域、地址栏、对话内容和任何唯一标识。处理完问题后删除临时排错文件。
